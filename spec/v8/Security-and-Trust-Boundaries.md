# Security and trust boundaries

## 1. Model is an untrusted planner

An AI model can propose a typed query, projection or mutation request. It is not the final authority for privileged effects.

```text
model proposal
   ↓
schema validation
   ↓
semantic validation
   ↓
authorization / capability / budget gate
   ↓
deterministic executor
   ↓
receipt/result
```

The same proposal must receive the same authorization outcome whether or not it was generated by a model.

## 2. Prompt/context taint

Retrieved documents, external web content, logs, emails, KOS text and tool outputs are data. Context items SHOULD retain:

- source/provenance;
- trust class;
- tenant/scope when applicable;
- sensitivity classification when applicable;
- retrieval reason.

Untrusted context MUST NOT redefine system policy, tool authority or approval requirements.

## 3. Schema validation is necessary, not sufficient

A valid JSON object may still reference nonexistent identities, violate semantic constraints, exceed authority scope or request an unsupported operation. Implementations distinguish at least:

```text
schema reject
semantic reject
authorization/capability reject
state/admission reject
```

## 4. Budgets and circuit breakers

AI/federated query execution has deterministic limits outside the model. Limits can cover time, items, bytes, tokens, shard fan-out and concurrency. Child queries consume parent budget.

## 5. Least capability

A query processor SHOULD expose only the capabilities required for the requested operation. A language resolver does not need mutation authority; an AI context compiler does not need canonical write authority.

## 6. Evidence and logs

Operational logs are useful for observability but are not canonical evidence unless admitted under an explicit Kristal evidence contract. Query receipts and fingerprints improve traceability without changing the authority of source data.
