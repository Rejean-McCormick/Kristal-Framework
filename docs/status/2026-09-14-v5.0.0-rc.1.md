## Executive status

Kristal Framework 5.0.0-rc.1 stabilizes the v5 corpus as a pinnable Git release while keeping the release machinery deliberately small.

The epistemic model remains Kristal v5. Release identity is based on **semantic version + Git tag + resolved immutable commit SHA**. The repository does not maintain a perfect inventory of every file and does not add a second repository-wide content-hash identity system on top of Git.

`contract-set.manifest.json` is a curated map of the public normative, profile, conformance, and informative surfaces. It exists so integrators know what constitutes the public Kristal contract; it is not a generated checksum catalog.

## Release identity model

A Kristal framework release is pinned by:

```text
semantic version
+ Git tag
+ resolved immutable Git commit SHA
+ canonicalization profile/version
```

For this RC:

```text
version: 5.0.0-rc.1
tag: v5.0.0-rc.1
commit: af703bf02ee04a69a5f2ad6694fa8b8e56ae2b19
canonicalization: kristal.v5:jcs-rfc8785
```

The tag names the release. The commit SHA identifies the exact repository tree. This is sufficient for Da'at, kOA, Konnaxion, Orgo, and IK to pin the framework without duplicating Git with a second repository-wide hashing system.

Kristal's own SHA-256/JCS rules remain normative where they belong: **artifact/content identity inside the Kristal protocol**.

## Downstream lock

A downstream integration SHOULD record:

```json
{
  "version": "5.0.0-rc.1",
  "git_tag": "v5.0.0-rc.1",
  "git_commit": "af703bf02ee04a69a5f2ad6694fa8b8e56ae2b19",
  "canonicalization_profile": "kristal.v5:jcs-rfc8785"

```

Floating dependencies such as `main`, `latest`, or `5.x` are not valid release locks.
