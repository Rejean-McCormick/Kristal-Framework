## Remaining Blockers

### K15 — Implementation Conformance

**Status:** BLOCKED

The normative EX/RP cases and executable framework TCK are present, but no external implementation adapter has yet been supplied.

The next implementation layer must expose equivalent operations for:

```text
build_exchange
verify_exchange
build_runtime_pack
verify_runtime_pack
```

LevelUpDiag should then execute the official Kristal vectors against that implementation rather than treating the framework vectors themselves as implementation proof.

A future successful result may support the claim:

> **Kristal reference implementation conforms to the declared Exchange and Runtime Pack contracts.**

That claim is not yet established.

### K24 — Cryptographic Trust Conformance

**Status:** BLOCKED

The framework defines signature/trust surfaces, but no executable verifier is currently available to prove the required fail-closed behavior.

The crypto/trust test suite should eventually cover at least:

- valid Ed25519 signature;
- invalid signature;
- wrong verification key;
- payload modified after signing;
- signature bytes modified;
- revoked key;
- expired or otherwise rejected trust state;
- trust-root/key rotation behavior where applicable.

Until those tests execute successfully against a real verifier, cryptographic trust conformance remains unproven.

## Release Model

The `v5.0.0-rc.2` release model now follows these principles:

1. Git tag + commit identify the immutable published release.
2. `contract-set.manifest.json` is a curated public-surface index, not a per-file hash inventory.
3. The retired `schema-set.manifest.json` and `tools/build_manifests.py` must remain absent.
4. Release archives are built from Git-tracked files.
5. Untracked diagnostics, temporary files, or external LevelUpDiag evidence must not affect release bytes.
6. `canonicalization_profile` and `canonicalization_version` are validated explicitly.
7. JSON Schema format checking must fail closed rather than silently accepting unsupported format checks.

## Identity and Conformance Boundary

Kristal distinguishes framework conformance from implementation conformance.

The current validated chain is:

```text
Normative documentation
        ↓
Schemas / identity profiles
        ↓
Golden vectors / framework TCK
        ↓
Framework validation
        ↓
PASS
```

The next required chain is:

```text
Official Kristal vectors
        ↓
External compiler/verifier implementation
        ↓
Exchange build + verification
        ↓
Runtime Pack build + verification
        ↓
Tamper / rebuild / determinism tests
        ↓
Implementation conformance
```

After implementation conformance, ecosystem validation can proceed through:

```text
Operational owner
        ↓
immutable snapshot/export
        ↓
Interaction Kernel
        ↓
Da'at
        ↓
Kristal Exchange
        ↓
Runtime Pack
        ↓
ArtifactRef / receipt
        ↓
operational consumer
```

These ecosystem E2E flows are not yet part of the current validation claim.
